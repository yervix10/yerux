## Methodology and fairness notes

- Every benchmark exists as `src/<name>.yx`, `src/c/<name>.c`, `src/rs/<name>.rs`, `src/go/<name>/main.go`, uses the same algorithm, 64-bit signed integers, and prints the same checksum (verified byte-for-byte before timing). No benchmark had to be dropped. Yerux has no `for`, no bit operations and no `Vec::with_capacity`/`vec![x; n]`, so all programs are written in the same `while` + `push` style (lists grow by pushing; no pre-sizing anywhere). `sieve` uses `List<Bool>` / `Vec<bool>` / `[]bool`.
- Sizes were raised above the brief where the run would otherwise be ~50 ms (fib(40) instead of 38, sort and matmul repeat 10 / 5 rounds with varying data, 8M string pushes, 6M allocations, 100k particle steps).
- Safety checks actually performed (this matters when reading the ratios):
  - Yerux: overflow check on every `+ - *` (a few provably safe ones are elided), division check, bounds check on every `get/set/at`, `pop`, `byte`.
  - `C gcc -O2`: no checks at all. `C gcc -O2 + checks` is the same source built with `-DCHECKED`: `__builtin_*_overflow` on every `+ - *` and an explicit bounds check on every list access. It is the closest like-for-like peer of Yerux.
  - `Rust release`: bounds checks on (Vec indexing) but NO overflow checks (release default); `Rust + overflow-checks` adds them. This is the second closest peer.
  - `Go`: bounds checks on, no overflow checks, GC. Allocation benchmark uses global sinks so escape analysis cannot stack-allocate; the Go GC cost is real and included.
  - C `alloc` uses a volatile sink and Rust uses `black_box` so the allocator calls are not optimised away; all heap lists/strings grow by doubling from 4 and are freed per iteration.
- `arith` is bound by the loop-carried chain through `% 1000003` (the checks are proven away by range analysis), so all seven land within noise of each other. Treat that benchmark as a tie.
- The machine is a noisy 2-vCPU VM; `spread` is (max-min)/median across the runs. Differences under ~15% are not reliable (best-of-7 on this VM varies by +-5% between invocations, and the median can sit 20% above the best because the other tenant of the 2 vCPUs is not idle); the Yerux-native gaps discussed below (sort, matmul, structs, mandelbrot: 1.3-1.7x) are repeatable across runs, smaller differences are not.
- Yerux native produces a ~5 KB static ELF with no libc: compile time is effectively zero and the binary size is not comparable to the others (Rust/Go link a runtime). Lists use `realloc`-style growth and the runtime is mmap based, so native RSS is at or below C's.
- Caveat: gcc turns `fib` into a partially unrolled/inlined loop nest, so `C` fib is roughly 2x faster than `C + checks`; Rust release shows a milder version of the same.

## Analysis

Ranking by geometric mean of best time vs `C -O2` (this run, 11 benchmarks): Rust release 1.09x, C+checks ~1.2x, Rust+overflow-checks ~1.1x, **Yerux native 1.19x**, **Yerux C backend 1.34x**, Go 1.74x. Yerux native does the checked-arithmetic and bounds-checked work of `C + checks` and is now at the level of plain C/Rust on most of the suite.

**Where native is at parity or ahead of `C -O2`** (within noise or better): `arith` (1.1x, a tie), `sieve` (1.00x; `List<Bool>` is 1 byte per element now), `strbuild` (1.06x; in-place `realloc` growth, RSS 68 MB vs 101 MB for C), `alloc` (0.92x; the own size-class allocator beats glibc `malloc`/`free` here and is 2.8x faster than Go's GC), `nbody` (0.94x), `dot` (0.94x), and `fib` (1.34x C, but 1.4x *faster* than Rust release, 2x faster than Go and checked C: recursion is inlined three levels deep by the IR inliner and the frameless/shrink-wrapped prologue avoids `push rbp` on the early-exit path). `fib` against plain gcc -O2 is the one place where the unchecked reference gets partial unrolling of the recursion that we do not do.

**Where native is still behind** (all repeatable):

1. `sort` 1.69x (worst benchmark). Merge sort over `List<Int>` with several lists live at once: more simultaneously live values (two source cursors, destination cursor, three list pointers and lengths) than the 9 allocatable registers (rbx, r8-r11, r12-r15), so the inner loops reload list pointers and lengths from the stack (this is my reading of the disassembly of the matmul inner loop, which shows the same pattern; the sort loops were not disassembled in detail), and every access keeps its bounds check.
2. `matmul` 1.65x. The innermost `k` loop has a load of `a[i*n+k]` and `b[k*n+j]`, two bounds checks, two overflow-checked add/mul (the `imul` result is data dependent, cannot be proven), and the same register pressure: `ptr`/`len` of both lists are hoisted by `memopt` but spilled, so each iteration does `mov rcx,[rbp-x]; cmp idx,rcx` and `mov rax,[rbp-y]` (L1 hits, but extra uops). gcc -O2 has no checks at all (1.0x) while the like-for-like `C + checks` is 1.81x, so native matmul (1.65x) already beats checked C. Rust with bounds checks only is 1.26x.
3. `structs` 1.43x: `step` is inlined and the particle is split into scalars (verified in `yerux ir --native`), so what remains is the cost of the checked `+`/`*` (a `jo` after each) and `abs`/clamp branches in the step body plus a few loop-carried values (the running offsets) spilled to the stack because the loop also keeps four fields and the accumulators live. `C + checks` is 1.08x and Rust 0.78x.
4. `mandelbrot` 1.28x: floats live in GPRs and are moved to xmm0/xmm1 around every SSE operation (`movq` in/out); there is no XMM register allocation, which gcc/rustc have. Pure float loops (nbody, dot) hide this because they are memory bound; the 200-iteration scalar loop does not.

**Code placement (measured, not a win everywhere).** An earlier `_start` change (+~100 bytes) was observed to slow `arith` by ~19% on another run although the hot loop was byte-identical, only at a different address. The backend now (a) pads the header of every innermost loop (target of a back edge between hot blocks) to 16 bytes with multi-byte NOPs when that costs at most 9 bytes, and (b) starts every function on a 16-byte boundary (`YERUX_ALIGN=0` / `YERUX_NO_FALIGN=1` disable them for A/B tests). Measured on this VM with the CPU-time A/B harness (9-21 interleaved runs per variant): loop-header alignment alone is neutral within noise on all of arith, fib, sieve, sort, structs, matmul, strbuild, alloc (arith: best 0.317 vs 0.317-0.321 s; sweeping the loop start over 16 different offsets 0..60 gave 0.317-0.332 s, i.e. no alignment sensitivity on this CPU, so the 19% effect could not be reproduced here and is probably specific to the host CPU's decoded-uop cache/loop-buffer behaviour). Function alignment is a repeatable win on `strbuild` (best 0.198 -> 0.174 s, median 0.240 -> 0.210 s over 21 runs ; cause not analysed further, presumably the entry alignment of the hot string-push helper) and neutral elsewhere, so both are on by default as cheap insurance: code is at most ~15 bytes/function larger, and the padding bytes are never executed on function boundaries.

**What the C backend shows.** Through gcc the Yerux semantics (overflow, bounds, drop) cost about the same as hand-written checked C: 0.9-1.5x on arith/sieve/sort/structs/alloc/nbody/dot. Its remaining deficits are `strbuild` (2.25x, its per-byte push helper does not inline as well as an unchecked `push`) and `matmul`/`sort` where gcc cannot hoist `len`/`ptr` out of the loops without a `restrict` alias fact.

**Checks are cheap relative to the rest.** In C, adding all overflow and bounds checks costs 1.0-1.2x except matmul (1.8x: the checks block vectorisation/hoisting) and fib (2.7x, mostly because the unchecked version is inlined/unrolled). Yerux's safety is not the bottleneck; the remaining native gaps are register pressure and float/xmm handling.

## What to optimise next (priority order)

1. **Allocator: more allocatable registers and memory operands for spilled values.** Use `cmp reg, [rbp+off]` / `add reg, [rbp+off]` for a spilled operand instead of reloading it into rcx/rdx, and consider r8-r11 as callee-save-free temporaries across loops without calls. Targets sort, matmul and structs.
2. **XMM register allocation for Float vregs** (keep Float values in xmm2-xmm15, no GPR<->xmm moves per operation). Targets mandelbrot and the float part of nbody.
3. Partial unrolling of self-recursive calls for `fib` (1.34x of unchecked gcc).
4. Loop-invariant bounds-check hoisting (`i*n+k < len` with a monotone `k`) to drop the per-iteration `Check` in matmul-style loops.
