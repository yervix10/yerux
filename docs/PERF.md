# Yerux benchmark results

Generated by `bench/run.py` (5 interleaved runs per binary for five workloads). Machine: 12 CPUs, `Linux 6.12.117+deb13-amd64`. All outputs verified identical to the C version.

CPU time = user+sys from `wait4`. `best`/`median` in seconds; `spread` = (max-min)/median over the runs (noise indicator); ratios are relative to plain `C gcc -O2` (lower is better; ratio of best / ratio of median). RSS = peak resident set (MB).

These measurements were collected on a shared build host while other regression suites were active. Treat high-spread entries as noisy; rerun this script on an idle host for tighter comparisons.

## Concurrency: persistent pool map

`python3 bench/concurrency.py --runs 5` compares the native backend's serial
loop with `thread_pool_map` on a four-worker persistent pool. Each run computes
four batches of 5,000 items; each item performs 12,000 rounds of the same
integer recurrence. It verifies identical output and reports median wall time
and child user/system CPU for five timed runs after one warm-up. Pool timings
include worker startup, four map/join barriers, result collection, and
shutdown. `bench/concurrency_pthreads.c` is a C reference with the same work
and per-worker local sums; compile it using
`gcc -O2 -pthread bench/concurrency_pthreads.c -o /tmp/concurrency-c` and run
with no argument for serial or any argument for four pthreads.

The previous pool benchmark was slower than serial because each map callback
created a capturing closure just to write one result. Native closure creation
allocates an environment and dropping it frees the environment. The native
allocator protects its shared arena and free lists with one global futex lock,
so this caused two globally serialized allocator operations per item. This is
not a GIL: callback arithmetic ran on the worker threads, but each callback
also waited on the allocator. Result writes additionally take the list's
mutex, while the shared reference count uses atomics. There is no per-item
stdout. The scheduler separately used to lock once per index; the previous
change batches these claims into chunks of roughly one eighth of the range per
worker.

`Locked<List<T>>.set_index` now does the typed list mutation under the mutex
directly, without allocating a capturing closure for every index. This keeps
the short result-write lock, but lets expensive callback work proceed outside
it. Measurements on the 12-CPU Linux host (five timed runs after warm-up):

| Background load at run | Workload | Wall | User CPU | System CPU | Pool wall / serial |
|---|---|---:|---:|---:|---:|
| load avg 5.21 / 5.42 / 5.13 | Yerux serial | 1.299 s | 1.298 s | 0.000 s | 1.00x |
| load avg 5.21 / 5.42 / 5.13 | Yerux pool, 4 workers | 0.334 s | 1.663 s | 0.000 s | 0.26x |
| load avg 3.89 / 5.10 / 5.02 | C serial | 1.136 s | 1.135 s | 0.000 s | 1.00x |
| load avg 3.89 / 5.10 / 5.02 | C pthreads, 4 workers | 0.292 s | 1.139 s | 0.004 s | 0.26x |
| low short-term load, 1.78 / 3.97 / 4.62 | Yerux serial | 1.298 s | 1.297 s | 0.000 s | 1.00x |
| low short-term load, 1.78 / 3.97 / 4.62 | Yerux pool, 4 workers | 0.334 s | 1.655 s | 0.016 s | 0.26x |
| low short-term load, 1.78 / 3.97 / 4.62 | C serial | 1.136 s | 1.133 s | 0.002 s | 1.00x |
| low short-term load, 1.78 / 3.97 / 4.62 | C pthreads, 4 workers | 0.288 s | 1.138 s | 0.002 s | 0.25x |

The pool's user CPU is about five times its wall time, confirming that more
than one core is doing work. Yerux and C both take about 0.26 of the serial
wall time (3.77x and 3.95x speedup respectively in the low short-term load
run). The moderate-load readings were collected while other workers were
building and testing; the low-load reading had a one-minute load of 1.78 on
12 CPUs, with a five-minute average of 3.97, so it was not a completely idle
machine. Use the recorded uptime load averages to interpret wall-time changes.
The benchmark includes result locking, startup, and shutdown rather than
timing only the recurrence.

### Allocation-heavy pool callbacks

`python3 bench/concurrency_alloc.py --runs 5` measures four batches of 5,000
callbacks, each creating and dropping 100 short strings. Before the TLS cache,
on a host with 12 CPUs and uptime load averages 4.43 / 3.89 / 4.35, five timed
runs after warm-up measured serial at 0.0315 s wall / 0.0310 s user / 0.000 s
system, and the four-worker pool at 0.2004 s wall / 0.4241 s user / 0.4460 s
system (6.37x slower). The high system CPU came from threads contending on the
global futex allocator lock for each small allocation and free.

The runtime now keeps one cached block per size class in each thread's TLS.
Allocations and frees that reuse a cached block do not take the global lock;
cache misses and overflow still use the shared lists and arena. Worker exit
returns cached blocks to the shared lists under one lock, so the cache does not
strand its blocks after the worker TLS is discarded. Repeating the same
benchmark on that host with load averages 3.60 / 6.04 / 5.68 measured serial
at 0.0311 s wall / 0.0307 s user / 0.000 s system and pool at 0.0098 s wall /
0.0448 s user / 0.000 s system (3.16x faster than serial). The system-time
counter rounded to 0.000000 s after the change, down from 0.4460 s before;
pool wall time changed from 6.37x slower to 0.32x serial. Background load
differed between runs; re-run both scripts under similar `uptime` load for
comparisons. These numbers include allocation, callback dispatch, result
writes, pool startup, and shutdown.

## Main measured bottlenecks

The three largest median slowdowns among Yerux backends in this run are below. Causes are code-path hypotheses from the benchmark structure; this host has neither `perf` nor Valgrind/callgrind installed, so no hardware-counter profile was available.

1. **hashmap (Yerux C backend 2.41x median vs C).** Map uses checked modular integer hashing, open addressing, and parallel key/value/hash lists; the pure C loop has fewer abstraction and safety checks.
2. **sort (Yerux native 1.40x median vs C).** merge-sort's indexed list access adds bounds checks and creates register pressure in the inner copy/merge loops.
3. **fannkuch (Yerux native 1.31x median vs C).** the benchmark's hot loop is a candidate for profiling.

### Hashmap integer-key follow-up

`bench/src/hashmap.yx` inserts and finds nonnegative `Int` keys. The old
`Hash for Int` path multiplied and reduced every key even though the table
already reduces hashes by its capacity. Nonnegative integers are valid hashes
directly, so the fast path now returns the key unchanged; negative keys keep
the normalized fallback. This preserves equal-key hash consistency and gives
sequential integer keys a well-distributed probe pattern.

The previous recorded reference was 33 ms native / 21 ms C. After the change,
five interleaved runs measured native at 22 ms median and the Yerux C backend
at 23 ms; C's median was 39 ms in that run (highly noisy, 68% spread; best
17 ms). The native best was 21 ms. The shared host was busy, so compare the
backend best times and rerun on an idle host for tighter medians.

### String and Text follow-up

Added `bench/src/textops.yx`, a 200k-iteration workload covering string
building/formatting, `find`, `split`, and `join` (about one million std
operations). The C reference performs equivalent work and verifies the same
checksum. `find_from` now computes the final candidate index once instead of
checking `i + needle_len` on every candidate; `split` and `join` cache
loop-invariant lengths.

Five interleaved runs before -> after on the shared host (median seconds):

| Backend | Before | After |
|---|---:|---:|
| C gcc -O2 | 0.041 | 0.042 |
| Yerux native | 0.081 | 0.083 |
| Yerux C backend | 0.066 | 0.070 |

The checksum matched C in both runs. There was no measurable speedup; the
small differences fit within shared-host noise. The remaining gap appears to
come from allocation/copy overhead in split/join and needs a capacity-aware
string builder to address safely.

## Compiler build profile

The host had neither `perf` nor `cargo-flamegraph` installed, and installing
system `perf` requires administrator credentials. The compiler has an
instrumented stage profile instead: set `YERUX_PROFILE=1` for a build to print
module loading, parsing, checking, optimization, backend generation, and C
compiler times. Run-pass timings are included for optimizer passes taking at
least 1 ms.

For `examples/15_collections.yx`, the C backend profile spent about 1,221 ms
in GCC (`-O2`), 7 ms in parsing, and 7 ms in type/ownership checking. The
native profile spent about 497 ms in optimization, 7 ms in parsing, and 8 ms
in checking. The optimizer trace identified repeated `rangeopt` analysis of
`main` as the dominant native cost. Range analysis now runs once in the first
optimizer round, rather than once per fixpoint round. Taking ownership of the
loaded token vector also avoids a full token-stream clone before parse;
compiler detection is cached for the process.

The three code-side costs addressed were repeated range analysis inside the
optimizer fixpoint, formatting the whole IR as debug text to detect convergence,
and cloning every loaded token before parsing. The optimizer now uses
structural block equality and runs range analysis once per optimization; the
parser takes ownership of the token vector. Compiler discovery is cached so
one build does not spawn the C compiler version check twice.

Median end-to-end build times (five runs after one warm-up, release compiler):

| Program | Yerux native | Yerux C backend |
|---|---:|---:|
| `examples/11_generics.yx` | 30.1 ms | 233.7 ms |
| `examples/13_numeric.yx` | 93.4 ms | 659.5 ms |
| `examples/15_collections.yx` | 607.5 ms | 1,339.7 ms |

`bench/selfhost.py target/selfhost/yerux-self` also compared the first ten
numbered examples: the sum of per-example median times was 1.922 s for the Rust
compiler and 2.081 s for `yerux-self`. That run overlapped other regression
work, so treat the totals as noisy.

These timings include C compilation for the C backend. Native optimization
for `examples/15_collections.yx` fell from 805 ms before the optimizer change
to 497 ms after it in the stage profile. These compile-time samples ran while
other regression suites were active and are noisy. The native backend avoids
the GCC step; the C backend retains `-O2` for generated program runtime
performance.
