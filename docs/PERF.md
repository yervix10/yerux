# Yerux benchmark results

Generated by `bench/run.py` (7 runs per binary, interleaved). Machine: 12 CPUs, `Linux 6.12.117+deb13-amd64`. All outputs verified identical to the C version.

CPU time = user+sys from `wait4`. `best`/`median` in seconds; `spread` = (max-min)/median over the runs (noise indicator); ratios are relative to plain `C gcc -O2` (lower is better; ratio of best / ratio of median). RSS = peak resident set (MB).

These measurements were collected on a shared build host while other regression suites were active. Treat high-spread entries as noisy; rerun this script on an idle host for tighter comparisons.

## Main measured bottlenecks

The three largest median slowdowns among Yerux backends in this run are below. Causes are code-path hypotheses from the benchmark structure; this host has neither `perf` nor Valgrind/callgrind installed, so no hardware-counter profile was available.

1. **strings (Yerux C backend 2.93x median vs C).** the workload repeatedly appends formatted integers; the Yerux C backend pays per-character helper and capacity-check costs.
2. **fib (Yerux C backend 2.71x median vs C).** recursive calls and overflow checks dominate this call-heavy workload; the C compiler optimizes the plain-C recursion more aggressively.
3. **hashmap (Yerux native 2.64x median vs C).** Map uses checked modular integer hashing, open addressing, and parallel key/value/hash lists; the pure C loop has fewer abstraction and safety checks.
